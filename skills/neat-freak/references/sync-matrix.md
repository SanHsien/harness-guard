# 變更影響矩陣（事實 → 檔案）

遇到不確定「這次的事實變更要同步哪些檔案」時查這張表。

**這是一份範本，不是規格。** 左欄是「你的工作裡會發生什麼事」，右欄是「那件事發生後哪些檔案就過期了」。下面的列是通用起手式，請換成你自己的事實類型與檔案結構——這張表只有貼合你實際的檔案佈局才有用。

## 事實層變更 → 檔案層變更

| 這次對話發生的事 | 要改的檔案 |
|---|---|
| 專案進度推進 | 對應專案主檔的進度段 · 日誌一行摘要 |
| 對外送出（提案 / 報價 / 交付物 / PR） | 該案主檔的「下一步」記「等回覆、何時追」 · 日誌記已送出 |
| 收到回覆 / 對方確認 / 拒絕 | 該案主檔狀態行 · 若結案則歸檔並更新索引 |
| 排程訂下或改期 | 主檔日期 · **外部系統（行事曆 / 排程工具）同步——只改本地不算完成** · 改期連帶檢查其他受影響待辦 |
| 金額 / 合約 / 條款變動 | 對應財務或合約檔 · 若影響既有結論則同步修正 |
| 新機會或新工作項第一次成形 | 建立該案的單一來源檔（SSOT）· 上層彙整檔只放一行摘要 + 連結 |
| 決策定案 | 決策檔標記為已定案 · **被推翻的舊結論刪除，不是加註** |
| 技術方案改變 | 程式碼旁的文件 · README · 規則檔（CLAUDE.md / AGENTS.md）中的相關敘述 |
| 規則或流程改變 | 規則檔本身 · 檢查是否有 hook / 腳本在執行舊版規則 |

## 使用原則

1. **一個事實只活在一個地方。** 同一件事寫在兩個檔案，遲早會 drift 成兩個互相矛盾的版本。上層彙整檔只放摘要與連結，不複製內容。
2. **狀態改變優先於新增內容。** 對帳的重點是「哪些既有敘述現在是錯的」，不是「還能補寫什麼」。
3. **外部系統算不算同步完成，看外部系統。** 本地檔案改了但行事曆／排程工具沒改，這件事沒有完成。
4. **刪除是合法動作。** 過期的結論、已被推翻的決策、已完成的待辦，留著只會讓下一個人（或下一次的你）讀到錯的答案。
