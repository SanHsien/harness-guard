# 審查迴圈

一個人要為一份不是自己寫的長文件簽名，而他的注意力有限。這個 skill 只做一件事：

> 讓**實際發生的變更**與**被人看見的變更**數量相等。

飄移的定義就是這兩個數字對不起來。有東西改了、甚至整段不見了，而審查的人從頭到尾不知道——那段不是被否決，是**從來沒進過任何人的視野**。

## 什麼時候用

使用者要審一份你寫的長文件，而且**會有第二輪**。第二輪一出現，飄移就開始了。

一次性的短回覆不用。單輪定稿也不用。

## 為什麼靠自律不行

這個 skill 存在的理由，來自一次真實失敗。一份長規格做了四輪，結果：

- 一整章在改版之間消失，沒有人發現
- 章節編號全面位移，v1 的「第 4 章」與 v2 的「第 4 章」是不同的東西
- 一個已經被口頭核可的章節，事後被改了標題、插入新小節、重新編號，核可的人不知道

事後派了一隻獨立的 AI 去做版本比對，它找到 9 個較小的遺漏，**卻沒發現整章不見了**。

原因不是它不夠仔細。是**散文裡「本來有、現在沒有」根本不存在**，沒有東西可讀。要抓那個，文件必須有結構身分，而且要用算的，不是用讀的。

所以：**不要叫 AI 去「找有沒有漏東西」，要讓機器對一個有分母的比率。**

## 七條規則

### 1. 每個區塊有永久代號

在 markdown 裡標一行：

```markdown
<!-- @block timeline -->
## 時間安排
內文……
```

代號出生時取一次，**之後永遠不能改**。標題可以改、順序可以換、內文可以整段重寫，代號跟著那塊內容走。

顯示的編號由工具生成，**不要手寫章節號**。手寫的編號一定會漂。

### 2. 移除靠宣告，不靠刪除

要拿掉一段，不要直接刪：

```markdown
<!-- @block old-section removed: 併進 timeline 了，這段的前提已不成立 -->
```

它會渲染成灰色刪除線，留在原地。**留著才看得見它被拿掉了。**

### 3. 變更由機器算，不由人記

跑 `check` 會算出覆蓋率——上一版的區塊有多少在這一版找得到下落。少一段就是比率掉下來，不需要有人「注意到」。門檻預設 100%。

狀態（新增／已改／未動／已核可／已移除）也是算出來的，比對內容雜湊，不用手填。手填的東西會忘記填。

### 4. 核可要凍結

使用者說某一段通過，那一刻的內容雜湊被記下來。之後那段如果被改了、狀態卻還是「已核可」，`check` 直接擋。

**核可不是一句話，是一個鎖。**

### 5. 回饋掛在代號上，意圖由使用者選

每個區塊一格意見，加一個意圖：**通過／改／問／討論**。

- 選「改」就照做，不要囉嗦，不要反過來說服他
- 選「問」就回答，**不要動文件**
- 選「討論」才進辯論模式，可以講你不同意
- 選「通過」就凍結

**不要預設要標「我同意／我不同意」。**要不要辯論取決於使用者當下想幹嘛，不是你決定的。他說改就是改。

### 6. 掛不到代號的意見，是結構問題

一條意見如果**掛不到任何一個區塊代號**，那通常不是某一段要改，是整份東西的形狀有問題。

- 「素材表這格寫錯段別」→ 掛得到 `materials`，照補就好
- 「這個不好賣」「每一段都沒有成果感」→ 掛不到任何一段，因為它講的是全局

**掛得到代號的，照做，不要囉嗦。掛不到代號的，停下來。**

停下來要做的是：先講出你認為他真正指到的是什麼，問他對不對，**得到確認再動結構**。不要自己逐條補——一條一條補會補成補丁，補完他還是覺得不對，而且你已經花掉一輪。

真實案例：一份分成多個階段的規格，被評「每個階段都在慢慢磨、這樣不好賣」。逐條補的話會去調整各階段的內容；正確的處理是回頭問「這個分階段的結構到底該不該存在」，結果整份改成單一階段完成。那一次的改善超過其他所有輪次加起來。

這條也是判斷「要不要跟他辯論」的依據：掛得到代號的意見不需要辯，掛不到的才值得。

### 7. 禁止隱式繼承

每一段都要能單獨看懂。不准寫「同上一版」「見前節」「同 v2，可跳過」。

這類參照在改版或歸檔之後會爛掉——歷史版本一收進 archive，那份「定版」就殘廢了。`check` 會抓這種寫法。

## 一輪長什麼樣

```
你寫／改文件（帶 @block 代號）
   ↓
render → 審查頁（每段一格意見 + 意圖選鈕，只有變過的需要看）
   ↓
使用者審（錄音或打字，見下）→ 一鍵複製回饋
   ↓
apply → 更新狀態、凍結核可過的、印出待辦
   ↓
你改 → check 過了才交出下一版
   ↓
交付時附一份白話的變更說明（見下）
```

### 指令

第一次用先確認路徑對不對——skill 裝在哪，腳本就在哪底下的 `scripts/`。

```bash
python3 ~/.claude/skills/review-loop/scripts/review_loop.py render spec.md   # 產生審查頁
python3 ~/.claude/skills/review-loop/scripts/review_loop.py check  spec.md   # 出版前閘門，有問題非零退出
python3 ~/.claude/skills/review-loop/scripts/review_loop.py apply  spec.md feedback.txt
```

回饋格式（審查頁的「複製」按鈕就是產這個）：

```
[timeline] 通過
[materials] 改 — 素材表寫「第二、三段」，但第二段沒有工具紀錄
[format] 討論 — 這個立基點我覺得要再想
```

## 兩種輸入，同一條路

**打字**：審查頁每段都有輸入格，填完按複製，貼回來。

**錄音**：適合長文件與需要邊想邊講的場合，一個小時的錄音可以講完幾十段的意見，比打字快得多，而且容易進入專注狀態。錄完轉成逐字稿貼回來就行。

轉錄用什麼工具**這個 skill 不管**——本機模型、雲端 API、或你已經轉好了直接貼，都可以。但有兩條保命規則跟工具無關，看 [references/transcription.md](references/transcription.md)。

收到逐字稿之後，你要做的是**把散落的口語意見逐條對應到區塊代號**，然後才動手。對不到代號的意見要問清楚是指哪一段，不要猜。

## 交付：每一輪都要有白話說明

改完之後不要只丟一份新文件過去。**看不懂的變更等於沒被看見**——它在「被人看見的變更」那個分子裡是零。

所以每一輪附一段白話說明，講清楚三件事：

1. 你講的哪幾條，我怎麼處理的
2. 我沒照做的有哪些，為什麼
3. 還有什麼沒解決

寫的時候：**不要中英夾雜、不要術語、不要縮寫**。專有名詞真的沒有中文就括號補一句白話。先講結論跟對他的意義，再講細節。寧可少講講清楚，也不要每個細節都塞——看不懂的根因通常是講太多，不是講太少。

比喻優先於定義。一句話講一件事。

## 收尾：定版必須自足

要把歷史版本歸檔時，**定版不准有任何指向歷史版本的指針**。

歸檔前跑一次 `check`。它會抓「同 v2」這類寫法——那正是文件會殘廢的地方。

歸檔的資料夾放一份說明，記三件事：每個版本為什麼被取代、決策的原始依據在哪（逐字稿、來源文件）、以及這次比對發現了什麼。

## 不要做的事

這些是刻意排除的，加進來就是過度設計：

- **不要做轉錄系統。**入口的事，不是本體。
- **不要規定回應總表的長相。**只要每條意見追得到代號、說明處置、看得出還剩什麼沒解決就好。
- **不要強制標同意／不同意。**取決於使用者當下想幹嘛（規則 5）。
- **不要規定跑幾輪，不要搞定版儀式。**收斂了就收斂了。
- **不要做 diff 檢視器。**灰掉 + 標記「這輪改過」就夠，不要做成程式碼比對工具。
- **不要派 AI 去找遺漏。**已經證明沒用。用覆蓋率。

## 選配

- `--strict-numbers`：把「同一個數字出現在多個區塊」從提醒升級成失敗。同一個事實寫在兩個地方，兩邊遲早各自漂成兩套說法（真實案例：同一份文件裡，一場活動在某節寫成免費、在另一節寫成收費）。文件裡有價格、日期、人數這類會被引用的數字時建議開。
- `--min-coverage`：放寬覆蓋率門檻。預設 1.0，**不建議調低**——調低等於允許東西無聲消失。
