# 使用者看得到的結果：檢查項與證據

這份是 SKILL.md 第 6 節的細節。適用於會被人直接看到或拿去用的結果：畫面、指令輸出、
產生出來的檔案、報告或筆記裡的數字與事實、安裝到其他 agent 的副本。它加在第 1 至 5 節
之上，不取代任何一節：測試照跑、結束碼照報，這裡只是補上「測試證明不了的那一段」。

出處：五條規則的想法改寫自 [lobehub/acceptance](https://github.com/lobehub/acceptance)
（Apache-2.0，審查 commit `5e9115d`）的驗收技能文件；只取規則的意思，文字與例子都是重寫的。
本機的評估與取捨見 `SanHsien/ai-inbox` 的 `docs/lobehub-acceptance-eval.md`（B1 至 B5）。

例子標「實例」的是本機真的發生過的事；標「示意」的是為了說明而舉的情境。

## 1. 先列檢查項，每項宣告要哪一類證據

動工前（至少在宣稱完成前）寫下：這次交付有哪幾個使用者看得到的結果，每一個要用哪一類
證據證明。證據類型只有幾種：截圖、錄影、指令原始輸出加結束碼、實際資料（檔案內容、查詢
結果、頁面上的數字）。完成時逐項對照，宣告的證據缺一類，那一項就是「未通過」或「未驗證」，
不能因為其他項都過了就算整體完成。

- **反例（實例，2026-11-20）**：子 agent 補讀社群貼文留言，平台計數比畫面上看得到的多幾則，
  它把同一篇的「引用貼文」數量拿來補平差額，寫成「全部讀完」。引用貼文算不算進計數，畫面上
  看不出來；那個數字是算出來的，不是看到的。
- **正例**：檢查項寫「留言數：計數 N 則、畫面顯示 M 則，逐則讀完」，證據類型是「實際看到的
  數字」。看不到的差額照實寫「差 K 則不顯示，引用是否計入無法確認，不拿來補差額」。

## 2. 測試綠燈不能代替打開看過

測試、lint、型別檢查、建置通過是必要條件，在報告裡寫一行（指令與結束碼）即可，不列為
使用者看得到的檢查項。它們只證明「程式沒有違反測試寫下的那些斷言」；斷言沒寫到的地方，
綠燈什麼都沒說。

- **反例（示意）**：改了產生 README 表格的腳本，單元測試與契約驗證都綠，回報「完成」；
  打開產出的 README 才發現某一欄整欄空白，因為測試只斷言「表格存在」與「欄位名稱正確」。
- **正例**：測試綠了之後，打開實際產出（產生的檔案、執行後的畫面、指令的完整輸出），找到
  這次改動的位置，確認內容是預期的值，回報時寫出「打開哪個檔、看到什麼」。

## 3. 不可能失敗的執行不算證明

一次驗證要有失敗的可能，才算證明了什麼。修 bug 時，先用修改前的程式在同樣前提下重現失敗
（看到紅），再用修改後的程式跑同一批輸入（看到綠）。修改前也會過的輸入，修改後通過不代表
修好了。

- **反例（實例，2026-11-20）**：修完一支掃描器，只拿一個樣本跑修改後的版本，結果正確就
  回報「掃描器修好了」。沒有確認那個樣本在修改前會出錯，也沒有涵蓋同一類問題的其他寫法。
- **正例**：把原本會出錯的每一類輸入各準備一個樣本，先用修改前的版本跑，確認每個都出錯；
  再用修改後的版本跑同一批，全部正確；另加幾個本來就正確的樣本，確認沒有改壞。手上真的
  只有一個樣本時，回報寫「只驗了一個樣本」，不寫「修好了」。

## 4. 截圖要實際打開看過

截圖檔存在、檔名叫 `after.png`、附了一句圖說，都不能支持「通過」。要有人（或 agent 用讀圖
工具）實際打開那張圖，確認畫面上看得到這次要證明的東西，回報時寫出圖裡實際看到什麼。

截圖前後都要過隱私檢查（規範：`SanHsien/agent-safety-checks` 的
`docs/multimodal-screen-privacy-spec.md`）：

- 截圖前：`python C:\GitHub\agent-safety-checks\tools\screen_privacy.py --title "<視窗標題>" --app <程式名>`，
  結果是 `blocked` 或 `nocap` 就不截。
- 截圖後先做 OCR，再跑 `python C:\GitHub\agent-safety-checks\tools\screen_privacy.py --ocr-file <OCR 文字檔>`，
  結果要求丟棄（`drop_image`）就刪掉那張圖，不送出、不提交。

- **反例（實例）**：用桌面自動化截 WebView2 視窗，截圖檔照樣產生，打開才知道整張全黑；
  若只看「檔案存在」就會拿一張黑圖當證據。
- **正例**：打開截圖，寫「設定頁右上角顯示『已儲存』，欄位值是 30」這種描述；看不到要證明的
  東西就換截圖方法或回報「未驗證」。

## 5. 量一個改過的值，證明跑的是工作目錄裡的程式

驗證之前，先確認正在執行的就是剛改過的那份：開發伺服器沒重啟、瀏覽器快取、舊的安裝副本、
另一個 clone、還在跑的舊行程，都會讓你對著舊程式驗證，然後得到假的通過。做法是挑一個這次
改過、而且看得到的值（新字串、新欄位、版本號、新的輸出行），在實際執行的環境裡量到它，
量到了才往下驗。

- **反例（實例，2026-11-20）**：要把這份技能更新到各 agent 時比對才發現，Codex 與 Antigravity
  安裝的 `verification-protocol` 比 repo 少一整節（第 5 節）。若在那兩個 agent 裡驗證新規則，
  讀到的是舊副本。
- **正例**：安裝後在每個 agent 的實際技能目錄裡找到這次新增的段落（例如這份檔案存在、SKILL.md
  有第 6 節），並比對與 repo 的雜湊一致；網頁改動則在瀏覽器裡讀到這次新加的文字後，才開始
  驗其他行為。

## 檢查項範本

宣稱完成前填一份，回報時一起附上。`狀態` 只用：通過、未通過、未驗證（沒跑到不是通過）。

| 編號 | 使用者看得到的結果 | 方法 | 預期 | 必要證據 | 狀態與實際看到的 |
|---|---|---|---|---|---|
| 1 | 設定頁儲存後重新整理，值還在 | 瀏覽器操作 | 顯示新值 30 | 截圖（已打開看過） | |
| 2 | `tool --help` 列出新旗標 | 執行指令 | 輸出含 `--dry-run` | 原始輸出與結束碼 | |
| 3 | 報告裡的留言數 | 逐則讀 | 計數與讀到的數字一致 | 實際看到的數字 | |
| 4 | 跑的是新版 | 量改過的值 | 讀到新加的字串 | 原始輸出 | |

測試、lint、建置：一行寫指令與結束碼，不列入上表。
